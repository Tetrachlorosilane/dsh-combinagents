## 2. 安全发现

### SEC-1（High）未认证的 `/bootstrap` + 不校验 `Host`/`Origin`

**位置**

- `src/http.js:181-188`：`GET /bootstrap` 在 token 校验之前直接返回 `{ token, version, platform, supported }`；
- `src/http.js:167-170`：只校验 `remoteAddress` 是否 loopback；
- `src/http.js:185-188`：其余路由只比较 `x-dsh-combinagents-token`；
- `index.js:75-93`：token 每个 Host 随机生成并注册到同一个 prefix；
- `docs/ARCHITECTURE.md:276-282` 声称“same-origin / loopback / token”，但实现没有
  任何 `Host` 或 `Origin` 校验。

**实机证据**（token 已省略）

```bash
curl -s -H 'Host: evil.example:60601' \
     -H 'Origin: https://evil.example' \
     http://127.0.0.1:60601/dsh-combinagents/bootstrap
# HTTP/1.1 200 OK
# {"token":"<redacted>","version":"0.1.0","platform":"win32","supported":true}
```

同一 token 带 `Origin: https://evil.example` 访问 `POST /state` 得到 `405`
（说明认证已通过，只是方法不允许），即写路由同样不校验来源。

**攻击路径**

1. 用户浏览器打开恶意站点；攻击者 DNS 把 `evil.example` rebinding 到 `127.0.0.1`
   （或用户通过本地反向代理/隧道暴露 GUI）；
   **前置**：攻击页必须与 GUI **同端口**（例如页面本身从
   `http://evil.example:60601` 加载）才能在 rebinding 后仍被视为同源；普通
   跨站 `fetch` 因响应没有 CORS 头而读不到 token（但请求仍会发出）。如果 GUI
   端口固定/可扫描，这个前置很容易满足；
   现代浏览器的 Private/Local Network Access 可能弹出权限或阻止部分
   public→loopback 请求，但各浏览器/版本行为不一致，不能作为唯一防线。
2. 页面同源 `fetch('http://evil.example:60601/dsh-combinagents/bootstrap')` 读到 token；
   服务端看到的是 `Host: evil.example:60601`，当前实现接受；
3. 之后所有 `POST` 都带 token、同源、`Content-Type: application/json`，无需 preflight；
   bridge 无法区分这是合法 tab 还是攻击者页面。

**影响**（token 持有者能做什么，按路由逐项核对）

- `GET /sessions`、`/titles`、`/summary`、`/state`：读取全部 session 标题、cwd、
  permission preset、原生父链、组合图、task 文本——**信息泄露**；
- `POST /add-node`、`/set-parent`、`/set-grant`、`/rename-node`、`/set-title`、
  `/create-task`、`/update-task`：篡改 overlay、授权关系与任务板；节点 label 与
  task 文本会被 `composition_list_agents` / `composition_task` 读进 agent 上下文，
  可作为**间接 prompt injection** 通道；
- `POST /clone-tree`、`/bud`：创建新 session、复制历史、消耗模型配额；每个成功
  clone 还会永久保留一个 live 根（见 PERF-4），可被反复触发做**资源耗尽**；
- `POST /delete-composition`：删除 overlay（不删 session），造成数据丢失。

> bridge 本身没有“直接发消息”路由，所以不是“一键控制 agent”；但读全量元数据、
> 改授权、克隆、注入 task/label 已经足以构成严重风险。

**修复建议**

1. **校验 `Host`**：只接受 `127.0.0.1:<port>`、`[::1]:<port>`、`localhost:<port>`
   （端口取 `req.socket.localPort`），或可配置的显式 allowlist；这是防 DNS rebinding
   的关键，因为 rebinding 后 `Sec-Fetch-Site` 仍是 `same-origin`。
2. **校验 `Origin`（若存在）**：拒绝非本机 origin；跨站请求即使带 token 也拒绝。
3. **`/bootstrap` 校验 Host 为 loopback，且（若存在）Origin 为同源**；同源 GET
   通常不带 Origin，因此 Host 校验是关键。更彻底的做法是把 token 注入
   `window.__DSH_BOOT__` 而不是暴露一个可 GET 的端点（但 Host 校验仍必须做，
   否则 rebinding 可读 HTML）。
4. 敏感写路由（clone/bud/message-adjacent/task）加**二次确认或短期 nonce**；
   对本地多进程威胁，考虑 per-profile secret + OS ACL，而不是“loopback 即可信”。
5. 在 `docs/ARCHITECTURE.md` 明确“loopback 不是认证边界；本地代理/隧道场景需要
   Host/Origin 校验”。

**回归测试建议**：`Host` 伪造 → 403；`Origin` 跨站 → 403；`/bootstrap` 无
`Origin` 的同源请求 → 200；`Host: localhost:<port>` → 200。

### SEC-2（High）`sync-native` / `auto-attach` 可让同一 session 属于两个 composition

**位置**

- `src/manager.js:992-1038`（`syncNativeTree`）：只检查
  `composition.nodes.some(node => node.sessionId === entry.id)`，即“是否已在**本**
  组合”，**没有** `resolveSession(entry.id)` 的跨组合检查；
- `src/manager.js:917-982`（`autoAttach`）：同样只看当前 composition；
- `src/manager.js:122-129`（`indexComposition`）：直接把 membership 指向新 root，
  允许静默覆盖；
- `src/manager.js:104-116`（`ensureMembership`）：加载时也不检测重复。

**复现**（独立脚本，使用真实 `createManager`）

```text
C2 has child-x: true
R has child-x: true
resolveSession(child-x) -> root-r
one composition invariant holds: false
```

步骤：

1. `root-r` 是组合 R 的根，原生子节点 `child-x` 存在于 R 的 catalog；
2. 用户把 `child-x` 手工加入另一个组合 C2（`addNode('root-c2', ...)`）；
3. 打开 R 的 tab（1 节点组合会自动 sync）或点击 “Sync native agents”；
4. `syncNativeTree('root-r')` 看到 `child-x` 不在 R，就把它加进 R；
5. 现在 `child-x` 同时在 C2 与 R；membership 被 `indexComposition` 覆盖为 R。

`autoAttach` 的路径同理：`subagent/start` 的父在 R，而 child 已被用户加入 C2 时，
事件会把 child 再加进 R。

**影响**

- 直接破坏 AGENTS.md 的硬不变量“One session belongs to at most one composition”；
- 消息/中断授权按 composition 计算：C2 的边和 R 的边各自可以授权对同一 session
  的投递，**权限被放大**，且用户只以为自己建了一个组合；
- `resolveSession(child-x)` 只返回其中一个 root；另一个组合的 tab 从该节点打开时
  会解析失败或显示错误组合；
- `deleteComposition` 的 `unindexComposition` 只清理指向被删 root 的 membership，
  另一个组合仍包含该节点时，membership 直接丢失（后续 `resolveSession` 返回 null）；
- `/state` 的 `observations`/`grants`/`tasks` 在两边各自计算，UI 与授权语义不一致。

**修复建议**

1. 在 `syncNativeTree` / `autoAttach` 对每个 child 调 `resolveSession(childId)`：
   - `owner === null`：正常添加；
   - `owner.rootSessionId === root`：跳过；
   - 其他：**跳过并记录诊断**（系统事件不应静默“偷”节点），或显式走
     `addNode` 的跨组合移动语义（需要用户意图）。
2. `indexComposition` 在发现 session 已属于其他 root 时不要静默覆盖；至少
   `log.warn` 并在测试中失败。
3. `ensureMembership` 检测一个 session 映射到多个 record 的情况，作为损坏数据处理。
4. 为 `syncNativeTree` / `autoAttach` 增加跨组合测试（当前测试只覆盖同组合）。

### SEC-3（Medium）Task 的“用户创建”伪造与跨成员修改

**位置**

- `src/manager.js:577`：`createTask` 硬编码 `createdBy: 'user'`；
- `src/controls.js:854-861`：composed 的 `composition_task create` 直接调
  `manager.createTask`，因此模型创建的 task 也被标成用户创建；
- `src/manager.js:591-621`：`updateTask` 只校验 `rootSessionId` 和 revision，
  **不校验调用者是否 task 的 owner/祖先**；
- `src/controls.js:863-872`：`composition_task update` 允许任意组合成员对任意
  `taskId` 执行 start/complete/reopen/delete；
- `src/controls.js:842-845`：tool 输出/render 不显示 `createdBy`。

**影响**

- 被 prompt injection 的子 agent 可以创建“看起来是用户下达”的任务，父 agent
  或其它 agent 读取任务板时会提高信任度（**provenance spoofing**）；
- 任意成员可以完成/重开/删除用户或其它 agent 的 task，协调状态可被单方面篡改；
- 审计行 `kind: 'task'` 没有 actor，事后无法区分 user 还是 agent。

**修复建议**

1. `createTask` 接受 `createdBy`/`actor` 参数；tool 路径传 `agent:<sessionId>`，
   HTTP 路径传 `user`；clone 保持 `clone`。
2. `updateTask` 增加 actor 与权限：至少要求 owner 本人、其组合祖先，或显式
   `allowTaskManage` 能力；对 `delete` 更严格。
3. tool 输出/render 明确显示 owner 与 createdBy；审计记录 actor。
4. 对 task 的 `subject`/`description` 标注“agent 提供的内容”，避免下游模型
   把它当系统指令。

### SEC-4（Medium）`moveAcross` 丢更新与非原子跨记录移动

**位置**

- `src/manager.js:692-737`：`moveAcross` 在 `withMergeLock` 内直接
  `requireRecord(targetRoot)` → `attachSubtree` → `save(targetRoot)`，
  **没有获取 `targetRoot` 的 per-root 锁**；源 record 同样在无锁下保存/删除；
- `src/manager.js:216-238`：`withLock` 只串行化同一 root 的普通变更；
  `withMergeLock` 只串行化 merge，两者互不覆盖。

**复现**（独立脚本，延迟 `store.put` 制造交错）

```text
target nodes: s-tgt,s-b
lost update: true
```

时序：

1. A：跨组合把 `s-b` 移入 target，读到 target 旧 record，进入 `save`（被延迟）；
2. B：对同一 target 做普通 `addNode('s-new')`，拿 `withLock(target)`，读到旧
   record，加入 `s-new`，保存成功；
3. A 的延迟保存落地，用不含 `s-new` 的 record 覆盖，B 的更新丢失。

**影响**

- 两个 tab/两个客户端同时编辑时，节点、label、grant 可能静默丢失；
- 更严重的是非原子：`save(target)` 成功、`save/delete(source)` 失败（进程崩溃、
  storage 错误）时，subtree 可能同时存在于两个 composition，造成与 SEC-2 类似的
  重复归属与授权放大；
- `moveAcross` 删除/重键源组合时不迁移/删除 task、policy、clone 记录：
  源 root 的 task 变成不可达孤儿，policy 留在旧 key，clone 记录不清理。

**修复建议**

1. 采用固定顺序获取 `withMergeLock` + 两个 root 的 `withLock`（例如按
   rootSessionId 字典序），在锁内重读两个 record，再计算、保存；
2. 至少让 `moveAcross` 获取 target/source 的 per-root 锁，并让所有普通变更也
   经过同一把锁；
3. 引入补偿/事务日志：target 保存失败或 source 删除失败时回滚；或在 storage
   domain 支持跨表事务前，明确“移动不是原子操作”并在失败时重建 membership；
4. 移动/删除 root 时同步迁移或删除 tasks、policy、clones。

### SEC-5（Medium-Low）跨工作区审批只比较 `cwd`

**位置**

- `src/controls.js:283-288`：`crossesWorkspace` 只比较
  `callerSession.header.cwd` 与 `targetSession.header.cwd`；任一缺失即视为跨区
  （fail-closed），相等则视为同区；
- `src/controls.js:621`：非 live 目标用 `{ header: { cwd: target.cwd } }`，
  即组合里 attach 时的快照；
- `src/controls.js:622-634`：只有 `crossesWorkspace && !hasFullPermission` 才审批。

**问题**

- 两个 session 的 cwd 相同，但 sandbox mode、permission preset、approval policy
  可能不同；同 cwd 不等于同一安全域；
- 目标非 live 时，`target.cwd` 可能是旧快照；cwd 在 attach 后变化（或 workspace
  重新绑定）会让审批被错误跳过/触发；
- 相等比较区分大小写/分隔符（`C:\Work` vs `c:\work`）会多触发审批（fail-closed，
  可接受），但快照风险是 fail-open。

**修复建议**

- 用 live `Session` 的 `sandboxPolicy.resolve`、`permissionPresets.current`、
  `approval.overrideOf` 以及 workspace registry 成员关系判断“同一安全域”；
- 目标非 live 时默认要求审批（fail-closed），或用新鲜观测替换组合快照；
- 明确“跨工作区”的定义（workspace id，而非路径字符串）。

### SEC-6（Medium-Low）手工连边默认双向消息 + composed 模式跨原生树

**位置**

- `src/manager.js:273-292`：`grantManualConnection` 默认

- `src/manager.js:511-519`：delegation 建边默认 `allowMessage/allowInterrupt` 都为 true；

**影响**

**修复建议**

### SEC-7（Low-Medium）原生 `sendMessage` 失败后的裸回退

**位置**

- `src/controls.js:501-511`：`deliverNative` 捕获**所有**错误；只要
  `signal` 未 abort 就返回 `null`；
- `src/controls.js:635-646`：`native === null` 时直接
  `targetAgent.followup/steer(envelope)`。

**问题**

- 原生 `sendMessage` 的拒绝可能不是“目标不在我的原生树”，而是权限/容量/归档/
  策略拒绝；当前实现会把这些一并当成“不适用”，回退到裸 `followup`/`steer`；
- 回退路径只经过 `crossesWorkspace` 审批（见 SEC-5），同 cwd 时可能没有审批；
- 结果是原生层的一道授权检查被组合授权替代，属于“设计上的 bridge”与“意外绕过”
  之间的灰区。

**修复建议**

- 区分错误码：只在 `NOT_NATIVE_TREE`/`UNSUPPORTED` 等“不适用”错误上回退；
  对 `UNAUTHORIZED`/`ARCHIVED`/`CAPACITY` 等直接失败；
- 回退前重新检查 `crossesWorkspace` 与 target 的 sandbox/permission；
- 记录 `nativeError` 到审计，便于区分“原生拒绝后回退”和“正常投递”。

### SEC-8（Low-Medium）先读 body 再校验 token；重路由无速率限制

**位置**

- `src/http.js:415-443`：`createNodeHandler` 先 `await readBody(req)`，再
  `api.handle`；`api.handle` 才检查 loopback/token；
- `src/http.js:450-463`：`readBody` 最多缓存 128 KiB，超限抛 `PAYLOAD_TOO_LARGE`；
- `src/http.js:383-398`：`/clone-tree`、`/bud` 直接调用 clone adapter，无并发限制；
- `src/http.js:207-237`：`/titles` 最多 100 个 id，`readTitleSnapshots` 会读日志。

**实机证据**

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  -H 'content-type: application/json' --data-binary @140kb.txt \
  http://127.0.0.1:60601/dsh-combinagents/create
# 413  ← 在 token 校验之前就读完了 body
```

**影响**

- 未认证的本机进程（或本地代理后的远端）可以迫使 Host 为每个请求缓冲最多
  128 KiB；并发连接下是可观的 CPU/内存消耗；
- `POST /clone-tree` 可被 token 持有者（或 SEC-1 的攻击者）反复触发，每次创建
  整棵 session 树并保留 live 根；没有 per-root 的 clone 锁或配额；
- `/titles` 对 100 个持久大日志最坏约 20 s（每个约 200 ms），可被用来占满
  Host 的 I/O/事件循环。

**修复建议**

- 先校验 `Content-Length`（若存在）≤ `MAX_BODY_BYTES`，再校验 loopback/token，
  最后才读 body；超限直接 `req.destroy()`；
- `POST` 校验 `Content-Type: application/json`；
- 对 `/clone-tree`、`/bud` 加 per-root 互斥（409 `CLONE_IN_PROGRESS`）与配额；
- 对 `/titles`、`/external` 加单飞/缓存与最大 id 数（已有 100，可再降）；
- 加简单的 token-bucket 速率限制（按 remoteAddress/token）。

### SEC-10（Low-Medium）relay 信封的发送者名字可被模型影响

**位置**

- `src/controls.js:454-465`：`senderName` 优先返回 `callerNode.label`；
- `src/controls.js:473-489`：`deliver` 把 `Agent ${senderName} sent a message:` 写进
  目标上下文；
- `src/manager.js:946-948`：`autoAttach` 用 `info.label` 设置/重命名节点 label；
- `src/controls.js:368-374`：`startDelegation` 把 `started.name` 作为 label 传给
  `autoAttach`，而 `name` 是模型在 `subagent` 调用里可选的。

**问题**

- 一个子 agent 可以把自己命名为与受信任兄弟相同的名字（原生 name 只保证
  `[a-z0-9-]` 且 ≤32，不保证跨分支唯一）；relay 信封只显示这个 label，
  `senderSessionId` 虽真实但模型未必核对；
- 组合 UI 也可能把该 label 显示成“受信任的 reviewer”；
- label 不只来自受约束的 `name`：`nodeFromSummary` 会把 session title 作为
  label（`src/manager.js:59-70`），title 可以包含换行/控制字符；`senderName`
  直接把它拼进 `Agent ${label} sent a message:`，目标模型会看到可伪造的
  “系统/身份”文本（prompt injection/格式伪造）；
- 属于 agent 间的身份混淆/社会工程，不是远程代码执行，但在 prompt injection
  场景下会放大影响。

**建议**

- 信封使用稳定身份（`native path` / `sessionId` 短码）作为主标识，label 只作
  展示并标注“display name”；
- 对 label 做单行化（去除回车/换行与控制字符）、长度截断，并用明确的分隔符/
  `source` 字段隔离，避免把 label 当指令；
- `autoAttach` 不要用模型提供的 name 覆盖已有 label；至少保留原 label 并附注；
- `list_agents`/`send_message` 输出中明确 label 的不可信来源。

### SEC-11（Low）loopback 不是认证边界

**位置**

- `src/http.js:76-80`：`isLoopback` 只看 `req.socket.remoteAddress`；
- `index.js:76`：token 每个 Host 生成，但 `/bootstrap` 对任何 loopback 请求返回。

**问题**

- 同机任意进程（恶意插件、扩展、其它应用）都能拿到 token；本地反向代理/隧道
  （ngrok、Caddy、Vite dev proxy）从 `127.0.0.1` 转发时，远端也会被当成 loopback；
- DSH 的 `dsh-host-webserver` 本身不校验 `Host`/`Origin`（本次从 asar 源码确认），
  所以不能依赖上层。

**建议**

- 文档明确“local-profile 的安全边界是同机用户”；
- 远程/代理场景使用 per-profile secret（文件 ACL 保护）或显式 `--allow-remote`
  模式 + Host/Origin allowlist；
- `/bootstrap` 至少要求同源 `Origin`/`Host`，并考虑把 token 放进启动注入的
  boot payload。

### SEC-12（Low-Medium）Clone 的权限漂移与失败清理

**位置**

- `src/clone-manager.js:202-241`（`createRoot`）：只设置 `cwd`/`agentPreset`，
  不显式设置 permission preset；
- `docs/CLONE-SPIKE.md` 已记录：“Permission events must be present in the copied
  prefix; older sessions without them fall back to current defaults”；
- `src/clone-manager.js:490-519`：失败时 `dispose` root、删 record/tasks/clones，
  但**已创建的 DSH session 不会删除**，`attachWorkspace` 也可能已执行；
- `src/clone-manager.js:420`：`title: `${source.title} (clone)``；源标题 120 字符时
  追加后超 120，`createComposition` 会抛 `INVALID_FIELD`，clone 失败（边界 bug）。

**影响**

- 旧会话没有 permission 事件时，clone 根可能以 profile 默认（更宽）策略运行，
  而它复制了源历史；这是“clone 不应提权”的残余风险；
- 失败后留下无 composition 的 session/workspace 归属，用户看到“孤儿”；
- 120 字符标题的 clone 失败是可用性 bug。

**建议**

- clone 时显式记录/校验目标 permission preset；没有源事件时要求用户确认或
  复制源观测到的 policy（通过合法 API，而不是直接写事件）；
- 失败清理记录并提示“已创建的 session 未删除”，或实现 DSH 支持的补偿删除；
- 对 `${title} (clone)` 做 120 字符截断/后缀替换，并加测试。

### PERF-1（High）`/summary` 与 `/external`：未缓存的 `listDescendants`

**位置**

- `src/discovery.js:376-409`（`listNative`）与 `:416-429`（`countNative`）都调用
  `ctx.get('subagents').listDescendants(rootSessionId)`；
- `src/discovery.js` 没有为 `listNative`/`countNative`/`listTree` 设置任何缓存；
- `client.js:1334-1341`：`CompositionHeaderAction` 在每次 `sessionId`/`revision`
  变化时调用 `/summary`；
- `client.js:1022-1031`：`openPicker` 用 `Promise.all([/sessions, /external])`，
  `/external` 的 2.4 s 会**阻塞整个 picker 的首次渲染**。

**实测**：16 节点树，`/summary` 连续三次 2361/2274/2296 ms，root 版
2519/2495/2353 ms；`/external(root)` 2417/2370/2423 ms；`/external(member)` 12 ms。
说明成本在“从根遍历原生 catalog”，且与组合节点数近似线性（约 150 ms/子节点）。

**影响**

- 每次切换到一个 16 节点团队的 session，header chip 要等 2.4 s；多个窗口/重复
  挂载会叠加；
- 打开“添加 session”选取器时，`/external` 让整个列表延迟 2.4 s；
- 该成本与 `/state`（150 ms）无关，不能再用“外围 UI 慢”解释。

**修复建议**

- 为 `countNative`/`listNative`/`listTree` 增加 per-root TTL 缓存（建议 5–30 s），
  在 `subagent/start`、`sync-native`、`remove-node` 等事件上失效；
- header chip 不需要精确的 native 计数：可只返回 `compositionNodes`，或把
  `subagents` 计算延迟到 tab 打开后；
- `openPicker` 把 `/sessions` 与 `/external` 分开渲染，先显示 session 列表；
- 若 DSH 有更轻量的 catalog projection/`listChildren`，优先用它；否则缓存是
  最小改动。

### PERF-2（Medium）`/state` 每次全量 `filterSessions`

**位置**

- `src/discovery.js:289-342`（`describeMany`）每次都调用
  `query.filterSessions([{ kind: 'id', values: unique }])`；
- `src/discovery.js:247-282`（`list`）对同一数据有 5 s `corpusCache`，但
  `describeMany` 完全不用它；
- `src/manager.js:159-184`（`resolveSession`）在 membership miss 时还会
  `discovery.describe` → `readTitleSnapshot`，为了拿 `nativeParentSessionId`
  却折叠整条日志的标题。

**实测**：1 节点 `/state` 141.7/142.6/144.0 ms；同 Host 的 `/tasks` 0.8 ms、
`/grants` 0.6 ms，排除 grant/task 成本；`/sessions` 冷 190 ms、热 4.6 ms，
说明 140 ms 就是 `listSessions`/`filterSessions` 的全量 corpus 列举。

**影响**

- tab 每次打开、每次 grant/task/rename 后的 `mutate` 都会重新 `/state`，每次
  ~150 ms；
- 对 603 个 session 已如此；session 数增长时线性变差；
- membership miss 的 `resolveSession` 还可能读大日志（见下），造成秒级延迟。

**修复建议**

1. `describeMany` 复用 `list()` 的 `corpusCache`（或加一个 2–5 s 的
   `filterSessions` 结果缓存），并对**已有的 live session 跳过** `filterSessions`；
2. `/state` 直接复用 handler 已经读到的 record，避免 `getGrants`/`getTasks`
   各自 `requireRecord` 再读一次；
3. `resolveSession` 用“只读 header”的查询（`filterSessions`/`listSessions` 缓存）
   获取 `nativeParentSessionId`，**不要**为了解析归属而 `readTitleSnapshot`
   （后者会加载完整日志折叠标题）；
4. 对 256 节点上限的 `/state` 已可接受（合成 199 KiB、2 ms 内存 store），真正的
   瓶颈是 corpus 列举，不是图序列化。

### PERF-3（Medium）`/titles` 的持久会话标题折叠

**位置**

- `src/discovery.js:207-237`：`titles` 对最多 100 个缺失 id 调
  `query.readTitleSnapshots(missing)`；
- DSH `readTitleSnapshots` 会加载每个持久会话的完整日志并折叠标题（本次从
  asar 的 `dsh-session-query` 源码确认）；
- `client.js:997-1011`：每 10 个 id 一个 chunk，最多 30 个可见行，`Promise.all`。

**实测**：10 个持久会话首次 2087 ms，热（30 s 内）1.2 ms；按 100 个上限最坏
约 20 s；client 一次打开最多 3 个 chunk（30 个）≈ 6 s。

**影响**

- 选取器先显示 id，标题要等数秒；大日志越多越慢；
- 100 个 id 的请求可被 token 持有者用来占满 I/O。

**修复建议**

- 增加/延长 `titleCache`（30 s 已有，但首次仍慢）；对同一批 id 做 in-flight 合并；
- 只请求**当前可见**的 10–15 行，而不是一次 30；
- 若 DSH 持久层有标题索引，优先用索引；否则在 UI 接受“先显示 id”；
- 对 `/titles` 加最大 20 个 id 的限制（当前 100）。

### PERF-4（Medium）`rootHandles` 永久保留 clone 根

**位置**

- `src/clone-manager.js:79`：`const rootHandles = new Map()`；
- `src/clone-manager.js:313`：每个成功 clone 执行 `rootHandles.set(root.id, root.handle)`；
- `src/clone-manager.js:569-579`：只有 `dispose()`（插件卸载）才遍历释放；
- `src/clone-manager.js:260`：`pendingSources.set` 成功后**不删除**；
- `deleteComposition`（`src/manager.js:1077-1090`）只删 composition/tasks/clones，
  不通知 clone-manager 释放对应 root handle。

**实测/现状**：本 profile 已有 **12 个 clone 记录**（可能跨多次 Host 重启）；同一
Host 进程内每次成功的 clone 都会保留一个 live 根。`tests/clone-manager.test.mjs` 也断言 `liveCount === 1` 且只在
`dispose()` 后归零。若根历史较大，重复 clone 会线性占用内存；删除 clone 根
组合也不会释放。

**修复建议**

- clone 完成后即可 `root.handle.dispose()`（session 已持久化，仍可 resume），
  只在 UI 需要“保持活跃”时短暂保留；
- 若必须保留，设上限/LRU，并在 `deleteComposition`/UI 删除时释放；
- 删除成功的 `pendingSources` 条目（除非明确用于同 Host 的 resume）；
- 暴露 `liveCount` 到诊断/管理接口，便于用户发现泄漏。

### PERF-5（Medium）Clone 无并发闸门、无总超时、不可取消

**位置**

- `src/clone-manager.js:298-520`：`execute` 没有锁/信号量；`/clone-tree` 与 `/bud`
  可并行；
- `:273`：每个 child `AbortSignal.timeout(30000)`，但没有整棵树的总超时；
- `:381-412`：depth-first 构建，每个 child 完成后 `dispose`；
- `:60-70`：`observe` 用 `query.observeSession` 读取**完整事件数组**，只为取
  `completedPrefix`；16 节点团队每节点都读一次大日志；
- HTTP handler 不监听 `req` 的 close/abort，客户端断开后 clone 继续。

**影响**

- 16 节点 clone 约 10 s（文档实测），大历史/慢磁盘可能超过 Node 的默认
  `requestTimeout`，客户端先断开、Host 继续建树；用户重试会重复 clone；
- 双击/多 tab 可同时克隆，资源翻倍；
- `observe` 的全量事件数组在大 transcript 上是内存峰值。

**修复建议**

- per-root clone 互斥 + 全局并发上限（例如 1）；返回 `409 CLONE_IN_PROGRESS`；
- 增加总超时/AbortSignal，并把 `req.on('close')` 传入；客户端断开即 abort；
- `completedPrefix` 若能在读取时流式截断（或 DSH 提供按 turn 读取），避免
  加载完整日志；
- 成功后释放 root handle（见 PERF-4）。

### PERF-6（Medium）缓存 TTL 与调用时长倒挂、无 in-flight 合并

**位置**

- `src/discovery.js:40-43`：`DESCRIBE_TTL_MS = 2000`；`src/discovery.js:158-181`
  `describe` 在调用**完成后**才写 cache；
- `src/discovery.js:218-229`：`titles` 同理，批量完成后才写；
- `src/discovery.js:416-429`：`countNative` 完全无 cache。

**现象**：`/summary` 对持久大会话首次 2.0 s；由于调用本身 ≥ TTL，下一次请求
大概率已过期，cache 很难命中；并发请求也没有共享 Promise，会同时读同一日志
（惊群）。

**修复建议**

- 为 `describe`/`titles`/`countNative` 增加 in-flight `Map<key, Promise>`，
  完成后保留 TTL；TTL 应大于典型调用时长（如 30 s）；
- 对 `describe` 的缓存 key 包含“只读 header”与“title”两种用途，避免为了
  parent 解析去读 title；
- 对 `countNative` 用 5–30 s TTL + 事件失效。

### PERF-7（Low-Medium）`syncNativeTree` 在锁内做重活 + O(n²)

**位置**

- `src/manager.js:992-1038`：`withLock(root)` 内 `discovery.listTree(root)`
  （16 节点约 2.4 s），然后每个 child `discovery.describe`（可能读日志），
  每次 `addGraphNode` 都 `assertComposition` 全图（O(n) 校验 × n 次）；
- `src/manager.js:692-737`：`moveAcross` 在 `withMergeLock` 内做图操作与保存。

**影响**

- `sync-native` 期间，同一 root 的所有普通变更（rename/grant/task）排队，
  UI 的 busy 状态可能持续数秒；
- 256 节点上限下 O(n²) 仍可接受（`validateComposition` 256 节点 ×100 仅 4.8 ms），
  但叠加 `listTree`/`describe` 后，主要成本是 I/O。

**修复建议**

- 先在锁外收集/校验（`listTree` + `describe`），再短暂持锁合并；或把
  `sync-native` 变成后台任务 + 进度；
- 批量 `describe`（一次 `filterSessions`）而不是逐 child；
- 合并为一次 `createComposition`/批量 `addNode`，减少重复全图校验。

### PERF-8（Low）`/state` 重复 `store.get`、task 全表扫描

**位置**

- `src/http.js:255-297`：`manager.state(root)` → `store.get`；随后
  `manager.getGrants()` → `requireRecord` → `store.get`；`manager.getTasks()` →
  `requireRecord` → `store.get`；
- `src/manager.js:526-530`：`getTasks` 调 `store.listTasks(root)`；
- `src/store.js:310-315`：`listTasks` 先 `[...table.entries()]` 再按 root 过滤，
  即 **O(全部 task)**；durable per-record 下 `entries()` 可能读所有 task 文件；
- `src/store.js:337-340`：`listClones` 同样全表，`deleteComposition` 会调用。

**实测**：当前 task 少，`/tasks` 0.8 ms；内存 50k task 时 `getTasks` ×20 为 55 ms，
说明是线性但常数不大；durable 模式的文件 I/O 可能显著放大。

**修复建议**

- `/state` 把已读出的 record 传给 `getGrants`/`getTasks`，避免重复 `store.get`；
- 给 task/clone 建 per-root 索引（storage domain 的 index/key prefix），或在
  内存维护 `Map<root, taskIds>`；
- `deleteComposition` 只按 root 删除，不要全表扫 clones。

### PERF-9（Low-Medium）打开 1 节点组合自动 `sync-native`

**位置**

- `client.js:943-952`：`/state` 返回 `composition.nodes.length <= 1` 且未 sync 过时，
  自动 `POST /sync-native` 再 `GET /state`。

**影响**

- 用户只是打开 tab，就会**隐式修改**组合（导入整棵原生树），并支付
  `listTree` + 每 child `describe` 的成本（16 节点可达数秒）；
- 与 SEC-2 叠加时，自动 sync 可能在用户不知情下把别处的 session 重复纳入；
- 首次打开因此至少两次 `/state`（2 × 150 ms）+ sync。

**建议**

- 把自动 sync 改为显式按钮/一次性提示（或只在用户确认后）；
- 若保留自动 sync，至少把它放到后台并在 UI 标明“正在导入原生子节点”；
- 先做 SEC-2 的跨组合检查，再自动导入。

### PERF-10（Low）存储增长与轮转

**位置**

- `src/manager.js:405-416`：`recordAudit` 每次 grant/task/message/interrupt 写一行；
- `src/store.js:275-288`：audit 按 UUID 一行；`listAudit` 全表；
- `deleteComposition` 不删 audit；`moveAcross` 不迁移 task/policy/clone。

**现状**：本 profile `storages/combinagents` 共约 290 KB：26 个 composition、
12 个 clone、10 个 task、46 条 audit（每表 per-record 一个文件）。
短期无碍；长期消息/任务多时，audit 文件和 task 表会线性增长，`listTasks`/
`listClones` 的全表扫描变慢。

**建议**

- audit 按天/大小轮转或归档；至少提供清理命令；
- 对 task/clone 建 per-root 索引；
- `deleteComposition` 清理 policy；`moveAcross` 迁移/删除源 tasks/policy/clones；
- 文档说明 audit 的保留策略。

### PERF-11（Low）Picker 无虚拟化 + header chip 每次挂载都请求

- `client.js:768-824`：筛选后一次渲染所有 session 行（本 profile 603 行）；
  10k session 时 DOM/布局成本明显；可加 `slice(0, 200)` 或虚拟列表。
- `client.js:1334-1341`：每个 session header 挂载都 `/summary`；结合 PERF-1/2，
  切换会话本身就是数秒级后台请求。建议 chip 只读组合节点数（membership 命中
  即可），或把 native 计数延迟/缓存。

## 5. 已确认“做对了”的部分

- **无 HTML 注入面**：`client.js` 没有 `innerHTML`/`dangerouslySetInnerHTML`/
  `eval`/`new Function`；所有用户/模型文本走 React 文本节点；`/titles`/label/
  task 文本不会被当作 HTML。
- **Token 不落盘**：client 只在模块变量里缓存 bootstrap，不用 `localStorage`；
  `callApi` 用相对 URL，参数经 `encodeURIComponent`。
- **Bridge 基础防护**：loopback 校验、128 KiB body 上限、`cache-control: no-store`、
  无 CORS 头、JSON 错误码稳定；非 loopback 403、无 token 401、超限 413 均有测试。
- **图模型**：`validateComposition` 覆盖重复 id/边、多父、环、悬空边、root 不在图；
  变更返回新对象、不修改输入；`assertComposition` 统一抛 `CompositionError`。
- **不写 DSH 元数据**：没有 `parentSession`/`catalog`/`cwd`/policy 的直接写；
  clone 通过 `agents.create`/`startActivation` 走原生 API。
- **存储降级**：storage domain 打开失败回落 memory 并警告；record schema 用
  graph validator 复用，无额外依赖。
- **Clone 深度优先**：规避 Host 8 个 active child 上限；child 完成后 dispose，
  根保持 idle（`delivery: 'caller'`）。
- **测试**：95 个测试覆盖图、clone 计划/adapter、store、manager、discovery、
  HTTP、controls、host 装配、client 注册与 bundle shape。

## 9. 结论

- **安全**：bridge 的“loopback + token + body cap”在单机单用户模型下是合理基线，
  但 **`/bootstrap` 未认证 + 不校验 Host/Origin** 使 token 可被同端口 DNS rebinding
  或本地代理/隧道获取；同时 **跨组合归属检查缺失** 破坏了本产品最重要的图不变量。
  这两项建议在下次发布前修复。
- **性能**：真正的瓶颈不是图模型（256 节点校验仅 0.05 ms/次），而是 **未缓存的
  corpus/native 遍历**：`/state` ~150 ms、`/summary` ~2.4 s、`/titles` ~2 s。
  这些都可以通过“复用已有 corpus cache + per-root native 计数缓存 + in-flight
  合并 + header-only 解析”在不改产品语义的前提下解决。
- **工程质量**：测试覆盖广、无运行时依赖、无 HTML 注入面、clone 失败清理和
  depth-first 构建都做得不错；新增回归测试应优先覆盖 Host/Origin、跨组合归属、
  `moveAcross` 并发与 clone 句柄生命周期。

### 10.3 新发现

#### X-1（High）`req.on('close')` 让所有请求的 AbortSignal 一开始就是 aborted，clone/bud 必失败

**位置**：`src/http.js:496-515`（`req.on('close')` / `controller.abort()`）、
`src/http.js:460-475`（`/clone-tree`、`/bud` 传 signal）、
`src/clone-manager.js:327`（`execute` 首行 `signal?.throwIfAborted()`）。

**根因**：Node 的 `IncomingMessage` 在请求体读完后就会发 `'close'`（不是只在客户端
断开时）；此时响应尚未 `end`，`res.writableEnded` 为 false，`controller.abort()`
在 `api.handle` 之前执行。实测普通 `POST /create`：

```text
outer-req-end
outer-req-close
handle-start aborted=true
handle-late aborted=true
res-finish
```

端到端伪 clone 端点：

```text
response 500 {"error":{"code":"INTERNAL","message":"internal error"}}
cloneManager saw: [{"id":"s-1","aborted":true}]
```

**影响**：真实 bridge 的 `/clone-tree`/`/bud` 每次开始前抛 AbortError、返回 500；
`withCloneSlot`、120 s 总超时、req 断开取消全部失效。单测直接调 `api.handle`，
没有捕获。

**修复**：监听 `res.on('close')` 而不是 `req.on('close')`，在
`!res.writableEnded` 时 abort；或检查 `req.complete`/socket。加真实
`http.createServer(createNodeHandler(...))` 测试：正常 clone 的 signal 未 abort，
客户端中途断开才 abort。

#### X-2（Medium）task per-root 索引在 task 改 root 后留下 ghost

**位置**：`src/store.js:422-430`（`putTask` 只 index 新 record，不 unindex 旧）、
`src/store.js:441-447`（`listTasks` 直接返回 bucket）、
`src/manager.js:775-806`（`migrateMovedSideTables` 改 `rootSessionId`）、
`src/manager.js:582-586`（`getTasks` 不按 root 过滤）。

**复现**（真实 `createStore` + `createManager`）：

```text
source before move: [ 'Moved work' ]
target after move: [ 'Moved work' ]
source after move: [ 'Moved work' ]      ← ghost
stored source root of task: [ 's-root' ]
```

**影响**：源任务板继续显示已移走的 task；源 task 无法更新（TASK_NOT_FOUND）；
`deleteComposition(source)` 不删它；target 删除后 ghost 仍留在内存索引；现有
manager 测试用过滤式 fakeStore，未覆盖真实索引。

**修复**：`putTask` 先读 previous → `unindexTask(previous)` → `indexTask(new)`；
`deleteTask` 从所有 bucket 移除；`listTasks(root)` 返回前过滤
`record.rootSessionId === root`；加真实 store move/delete 测试。

#### X-3（Medium，安全策略）composed `subagent` 绕过 DSH 的 model-selection policy

**位置**：`src/controls.js:318-350`（只调 `llm.resolveCallConfig`，未读
`subagent/model-selection-policy`）；`src/controls.js:740-771`（provider/model
始终暴露）。DSH 原生 `@deepseek-ai/dsh-tool-subagent/src/index.ts:282-297` 读取
`subagentModelSelectionPolicy(...)`；`model-selection-state.ts` 明确：没有 policy
时显式选择只能使用当前父 route，且只有 `modelSelection: true` 才暴露字段。

**影响**：未 opt-in 的 session 中，composed 模型仍可请求任意 provider/model；
`resolveCallConfig` 只验证 route 可解析，不验证该 session 的授权 route。可导致
数据发往未授权 provider/模型、额外费用、绕过桌面端 allowlist。

**修复**：读取该 projection，按原生规则“缺省只允许父 route / policy 白名单”
执行；未启用 modelSelection 时从 schema/描述移除 provider/model 或拒绝；
加“无 policy 时非父 route 必须拒绝”的测试。

#### X-4（Medium）composed `wait_agent` 缺少“已报告 input”去重，`run_code` 循环空转

**位置**：`src/controls.js:399-447`：`agent.inbox.nextStep` 非空就立即
`resolve({timedOut:false})`。DSH 原生 `wait-agent.ts:35-95` 用
`reported: WeakMap<Agent,{rootCallId,ids}>`，同一 `exec.rootCallId` 内同一批
pending 不会再次立即返回；插件没有。

**影响**：`run_code`/程序化循环里 pending input 在 tool call 结束前不送达模型；
插件每次 wait 都返回 `timedOut:false`，形成忙循环/CPU 空转，甚至无限循环。原生
还会在 plugin unload 时通过 lifetime abort；插件没有。

**修复**：复制 `reported`/`exec.rootCallId` 逻辑，传入并监听 plugin lifetime；
加“同一 root call 内两次 wait，同一 pending 第二次应等待/超时”的测试。

#### X-5（Medium，性能）composed `subagent`/`fork`/`list_agents` 未声明 `isConcurrencySafe`

**位置**：`src/controls.js:528`（listAgents）、`:740`（subagentTool）、`:757`
（forkTool）没有 `isConcurrencySafe`；DSH `@deepseek-ai/dsh-tools/src/pipeline.ts:108-116`
默认 `exclusive`；原生 `list_agents`/`subagent` 明确 `isConcurrencySafe: () => true`。

**影响**：composed 模式下同一 assistant message 的多个 `subagent` 调用被串行执行，
违背插件 prompt 的“Start independent delegations ... together”，增加多 agent 启动
延迟；`list_agents`/fork 同样被串行化。

**修复**：对 `listAgents`、`subagentTool`、`forkTool` 加
`isConcurrencySafe: () => true`；`waitTool` 按原生语义决定；加定义断言。

#### X-6（Medium）clone root 上限驱逐可能 dispose 正在运行的 clone 根

**位置**：`src/clone-manager.js:343-352`：`while (rootHandles.size >
MAX_LIVE_CLONE_ROOTS)` 直接取最旧 handle 并 `dispose`，没有检查
`agents().get(oldestId)?.status`。

**影响**：用户可能已打开某个 clone 根并发起对话；下一次 clone 触发驱逐时，
`handle.dispose()` 会终止该根的活动 turn。测试只验证 `live.has(roots[0])===false`，
没有模拟 running。

**修复**：驱逐前检查 running；跳过 running，选下一个 idle；全部 running 时拒绝新
clone 或临时超限；加 running-root 驱逐测试。

#### X-7（Medium-Low）`/summary` 把 composition 节点数伪装成 `subagents`

**位置**：`src/http.js:298-313`（`subagents: compositionNodes`、`available: true`）；

误判；`available: true` 在 subagents 服务缺失时也不真实。这是 API 语义回归。

**修复**：返回 `compositionNodes` + `nativeSubagents`；`subagents` 保留 native
语义（缓存/懒加载）或改名并弃用；`available` 反映真实可用性；client 明确口径。

#### X-8（Medium-Low，安全/审计）audit 从 append-only 变成每 100 次裁剪到 5000 条

**位置**：`src/store.js:26`（仍写“append-only”）、`:203`（`AUDIT_LIMIT=5000`）、
`:326-337`（`pruneAudit` 删最旧）、`:400-409`（每 100 次 `appendAudit` 调 prune）。

**影响**：审计不再 append-only；token 持有者/能发消息或改授权的 agent 可制造

**修复**：按时间/大小轮转**归档**而不是删除；保留不可变审计文件；按 root/actor

#### X-9（Low-Medium，兼容）composed `list_agents` 的输出形状/状态与原生不一致
